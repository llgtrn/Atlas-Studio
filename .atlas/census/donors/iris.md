## Mechanisms Census

### SemanticGraph node/edge/identity model

**Provider: mixed — .iris mirror in this repo (`src/iris-programs/repr/types.iris`, `abstract_machine.iris`) is verified; the canonical Rust definition (`iris-repr` crate, referenced by name in-source) is NOT present in this repository.**

Verified from source: node kinds are referenced throughout as integer tags 0–19 (README states "20 node kinds"); concrete tags recovered from code comments/usage include `0=Prim`, `5=Lit`, `7=Neural`, `8=Fold`, `11=Ref` (from `compile_pipeline.iris`'s rejection of graphs containing Ref nodes, and `abstract_machine.iris`'s kind checks). `repr/types.iris` defines an 11-variant *type* system (`Primitive, Product, Sum, Recursive, ForAll, Arrow, Refined, NeuralGuard, Exists, Vec, HWParam`), each carrying a numeric `kind` tag, mirroring — per its own header comment — "the Rust types module in iris-repr/src/types.rs." Graph mutation primitives (`graph_add_node_rt`, `graph_connect`, `graph_disconnect`, `graph_replace_subtree`, `graph_set_prim_op`, `graph_add_guard_rt`, `graph_add_ref_rt`, `graph_set_cost`) are exposed as language primitives dispatched to the runtime, not implemented in `.iris` — their actual semantics live in the unpublished native evaluator.

Could not verify: the full 20-node-kind enum's exact ordering/payload shapes, and edge representation (adjacency structure, whether edges are typed beyond parent→child DAG structure) — these are asserted in comments but their ground-truth implementation is the absent `iris-repr` Rust crate.

### Content-address derivation ("is it really BLAKE3?")

**Provider: mixed, and the answer is nuanced.** `src/iris-programs/repr/hash.iris` opens with: *"BLAKE3 content addressing for IRIS graphs. Mirrors the Rust hash.rs (542 LOC) in iris-repr."*

What is actually verified from the `.iris` source:
- A genuine, hand-coded, 7-round single-block BLAKE3 compression function (`blake3_hash`) is present, using the real BLAKE3/SHA-256 IV constants, the real `G` quarter-round mixing function (add/xor/rotr with rotation amounts 16/12/8/7), and the real message-word permutation schedule for all 7 rounds — this is a faithful (if manually unrolled) single 64-byte-block BLAKE3 compression, but it is only ever fed one 16-byte block (4 words, rest zero-padded) and its output is XOR-folded and **truncated to 64 bits**, not the standard 256-bit BLAKE3 digest.
- However, the functions actually used throughout the codebase for node/type/fragment identity (`compute_node_id`, `compute_type_id`, `compute_fragment_id`, `hash_mix`, `hash_u64`, `hash_bytes`) do **not** call `blake3_hash` at all. They use a separate, simpler `hash_mix` primitive — two BLAKE3 `G`-function invocations (not the full 7-round compression) with the real IVs — described in-source as "BLAKE3-based" mixing, not full BLAKE3.
- `repr/wire_format.iris` (the binary serialization spec) reserves a full **32-byte** field for `SemanticHash` (`Mirrors the Rust wire.rs (1,972 LOC) in iris-repr`) — i.e. the *canonical* Rust implementation is expected to produce a standard 256-bit BLAKE3 digest. The 64-bit truncated `hash_mix` scheme visible in the `.iris` mirror is therefore a reduced/performance-oriented variant used only inside the interpreted self-hosted layer, not the format IRIS's own wire spec documents as canonical.

**Verdict: content addressing is BLAKE3-derived by design and by the (unverifiable) Rust original's own field-width contract, but the only content-addressing code we can actually read and verify in this repository is a non-standard, 64-bit-truncated, partially-simplified derivative — not full BLAKE3 — used for the self-hosted `.iris` mirror path.** The authoritative 32-byte BLAKE3 implementation lives in the absent `iris-repr` crate and could not be inspected.

### Graph codec / serialization format

**Provider: mixed.** Two codecs exist:
1. `repr/wire_format.iris` — a documented, deterministic, little-endian binary wire format ("Mirrors the Rust wire.rs (1,972 LOC) in iris-repr"): magic `"IRIS"` (0x49524953), version, 45-byte fragment header, FragmentId (32B), TypeEnv/Node/Edge/Boundary/Import sections, 32-byte SemanticHash, optional ProofReceipt section, Metadata section. This is a real, detailed spec verified from source, but the Rust implementation that actually produces/consumes it is absent.
2. `codec/gin_encoder.iris` + `codec/graph_decoder.iris` + `codec/hnsw_index.iris` — a **GIN (Graph Isomorphism Network) + VAE neural encoder** that embeds a SemanticGraph into a latent vector for evolutionary search: per-node feature extraction (kind/opcode/arity), one message-passing round, sum/mean/max pooling to a 12-dim vector, VAE reparameterization (mu/log_var/z), plus an HNSW approximate-nearest-neighbor index over embeddings for retrieving structurally similar fragments during evolution. This appears to be genuinely implemented in `.iris` (no "Mirrors the Rust..." comment found on `gin_encoder.iris` itself, though `crossover.iris`, `embedding.iris`, `feature_codec.iris`, `neural_codec.iris`, `training_data.iris` in the same `codec/` directory do carry such mirror comments) — treat the GIN-VAE codec as IRIS-original but note most of its sibling codec files are declared mirrors of a Rust original, so provenance is mixed even within this one subsystem.

**Provider: verified structurally, opaque internally.** `bootstrap/iris-stage0` is confirmed (via `file`) to be a non-stripped, dynamically-linked x86-64 ELF PIE binary; `bootstrap.sh`'s own comment says *"The stage0 binary is the frozen Rust evaluator"* and instructs `cargo build --release --features syntax --bin iris-stage0` to rebuild it — confirming it is Rust-compiled, but **no Rust source for it exists anywhere in this repository.** `bootstrap/*.json` are precompiled outputs of the self-hosting pipeline (tokenizer/parser/lowerer/interpreter/compiler/self-interpreter/mini-eval), themselves produced by compiling the `.iris` sources in `src/iris-programs/syntax/` through the frozen stage0 binary (`bootstrap/rebuild-json.sh`). `bootstrap/iris-native` is a separately-built statically-linked ELF produced by `bootstrap/build-native`, which assembles a self-hosting binary by extracting compiled bytecode blobs from `.iris`-emitted output and hand-constructing raw ELF headers via an inline Python script — a genuinely unusual, verified-from-source self-hosting bootstrap technique (compile pipeline stages to bytecode via the frozen stage0, then splice them plus a hand-built startup stub into a freshly-assembled ELF file).

### Compiler passes

**Provider: mixed — the pass *sequence* and *names* are verified from `.iris` source; each individual pass's real/fast implementation is declared a mirror of the absent Rust `iris-compiler` crate.** `compiler/compile_pipeline.iris` states: *"Mirrors iris-compiler/src/lib.rs compile() function"* and enumerates the real 10-pass pipeline: (1) Monomorphization, (2) Defunctionalization, (3) Match Lowering, (4) Fold/Recursion Lowering, (5) Effect Lowering, (6) Neural Lowering, (7) Data Layout assignment, (8) Instruction Selection (CLCU micro-ops), (9) Register Allocation (ZMM/AVX-512 registers), (10) Container Packing (CLCU containers). The pipeline explicitly **rejects** graphs containing `Ref` nodes (cross-fragment references, kind 11) because "the CLCU execution model has no fragment resolution" — a genuine, verified architectural constraint. 60 files exist under `compiler/`, most individually implementing one pass or one pipeline stage in `.iris`, and most of the interesting ones (`compile_to_bytecode.iris`, `elf_wrapper.iris`, etc.) also carry explicit "Mirrors the Rust..." headers.

**Provider: genuinely IRIS-original and independently verified from source — the strongest, most concretely verifiable mechanism in this census.** `lean/IrisKernel/` contains 8 real Lean 4 files (2,941 total lines): `Types.lean`, `Eval.lean`, `Kernel.lean` (executable `def` versions of the 20 inference rules — explicitly noted in-source as mirroring `src/iris-kernel/src/kernel.rs`, another absent Rust path), `Rules.lean` (the `Derivation` inductive — the actual formal proof-theoretic rule set), `Consistency.lean` (14 theorem/lemma statements, **zero `sorry`**), `Properties.lean` (23 theorem/lemma statements, **2 `sorry`**, explicitly flagged in-file: *"temporarily marked with `sorry` and flagged with `-- PORT: ...`"*), `KernelCorrectness.lean` (6 theorem statements, **5 `sorry`**, in-file note: *"proofs marked `sorry` need porting to Lean 4.28 tactic conventions... The statements are correct; the automation needs updating"*), `FFI.lean` (byte-level `Cursor`/wire-format C-exported functions for the Rust↔Lean IPC bridge).

Grep-verified: **0 `sorry` in `Kernel.lean`, `Rules.lean`, `Eval.lean`, `Types.lean`, `FFI.lean`** (the 20 inference rules and their supporting type/eval machinery). **7 `sorry` total across `KernelCorrectness.lean` (5) and `Properties.lean` (2)** — these are correspondence/metatheory proofs, not the rule definitions themselves. ### Self-modification admission ("what gates a change before it's accepted?")

**Provider: IRIS-original `.iris` source, and the actual admission logic verified is weaker than the README's framing.** `meta/performance_gate.iris` defines the intended gate: (1) Correctness — 100% match on all observed test cases; (2) Performance — within a configurable max-slowdown ratio (default 2.0x = 200%); (3) N consecutive passing runs before deploy (`should_deploy` requires all gate results to be 1). This is a **test/trace-equivalence gate, not a proof-kernel gate** — nothing in `performance_gate.iris`, `meta/auto_improve.iris`, or `meta/self_modify.iris` calls into the Lean kernel or the `checker/` type/cost-checking modules as part of the hot-swap admission decision. The Lean proof kernel (via `checker/kernel_client.iris`) appears to be invoked for a separate verification tier (type-safety/cost-bound proof obligations), not wired into the observed self-modification acceptance path.

**Concrete correctness finding (falsifiable, read directly from source):** `performance_gate.iris`'s `performance_gate` function signature is `candidate test_cases rust_ns max_slow` — it takes **no `iris_ns` (candidate timing) parameter at all** — and its body computes `let spct = slowdown_pct rust_ns rust_ns in`, i.e. it calls `slowdown_pct(rust_ns, rust_ns)`, which by `slowdown_pct`'s own definition (`iris_ns * 100 / rust_ns`) always returns exactly 100 (parity) regardless of the candidate's actual measured speed. The same pattern recurs in `meta/auto_improve.iris`'s `improve_cycle`/`improve_loop`, which call `passes_gate cand_score 100 max_slowdown_pct` — hardcoding the slowdown term to 100 rather than passing a measured value. **As visible in this repository's `.iris` source, the performance half of the self-modification gate is a stub that always reports "parity" and therefore can never itself block a deployment** — only the correctness (100%-match) term is actually discriminating in the code we can read. Whether the real, native runtime performs the actual timing comparison (and the `.iris` mirror is simply an incomplete/illustrative reimplementation) could not be verified, since that runtime's source is absent.

### How optimized/evolved implementations retain identity and correctness

Two independent mechanisms, both partially verified: (1) content-addressed `FragmentId`/`NodeId`/`TypeId` (see hashing mechanism above) mean a semantically-identical rewritten subgraph is *structurally* re-identifiable/de-duplicatable by hash, independent of surface syntax — this is architecturally real and consistent with the wire-format spec. (2) A tamper-evident BLAKE3 Merkle-style audit chain is real in the `.iris` layer: `meta/instrumentation.iris` defines `verify_chain_link` (checks one entry's `prev_hash` against the prior entry's hash) and `verify_chain` (folds over an entry list, multiplying a running `valid` flag) — a genuine, if simple, hash-chain integrity check. However this audit-chain code only *verifies* link integrity given hash pairs; it does not itself compute canonical BLAKE3 hashes of arbitrary deploy-event payloads in the file inspected (that appears to depend on the same `hash.iris`/native hashing boundary already discussed).

## Atlas Comparison

### Content-addressed identity: Atlas `SemanticRecordId`/`RawObservationId` vs IRIS `NodeId`/`TypeId`/`FragmentId`

- **Atlas today (verified from `core/src/identity/mod.rs`, `core/src/semantic/observation.rs`):** `stable_id(prefix, identity)` is an **FNV-1a 64-bit hash** (`0xcbf29ce484222325` offset basis, `0x100000001b3` prime) over a string, formatted `"{prefix}:{hash:016x}"`. `SemanticRecordId` is derived from a semantic-family's `identity_key()` (the CLAIM identity — what the record is about, independent of the evidence that produced it). `RawObservationId` is derived separately, from `stable_id("raw-observation", &content)` where `content` combines `record_id`, extractor identity, evidence, status and payload — i.e. Atlas already runs a **two-tier identity split**: a stable semantic-claim identity vs. a distinct per-observation identity, so that the same claim observed twice by different extractors/evidence produces the same `SemanticRecordId` but different `RawObservationId`s. This split is real, tested, and in production (per task framing).
- **IRIS:** a single content-addressing scheme per artifact kind (`NodeId` from a node's full canonical representation incl. kind/type/arity/depth/salt/cost/payload; `TypeId` from type-tag+payload; `FragmentId` chaining graph/inputs/outputs/type-env/imports hashes) — content-address *is* identity, there is no separate "claim vs. observation" split, because IRIS graphs are purely functional/deterministic programs, not extracted facts about external source code with varying evidence quality. There is no epistemic-status or evidence-provenance dimension in IRIS's identity model at all (unsurprising: IRIS identifies its own programs, Atlas identifies facts *about* other people's programs).
- **Assessment:** these are solving **different problems, not the same problem differently.** Atlas's split exists because the same semantic claim can be observed multiple times with different evidence/extractor/status; IRIS's single content-address exists because its own graph nodes are the ground truth with no separate "observation of an observation" concern. Where they are comparable: **hash algorithm strength.** Atlas's `stable_id` is FNV-1a — fast but not collision-resistant, adequate for a bootstrap non-cryptographic dedup key at Atlas's current scale but explicitly weaker than IRIS's (aspirational/partially-verified) BLAKE3-based scheme. This reinforces, but does not add new evidence beyond, Atlas's **already-admitted `blake3` donor** (`.atlas/provenance/donors/blake3.json`, `target_owners: ["compiler","runtime/binary","core/atlas-format"]`), which already targets exactly this upgrade path. IRIS is not a novel source of this idea for Atlas.

### Graph representation: Atlas `UniversalGraphContract`/`engineering_graph.rs` vs IRIS SemanticGraph

- **Atlas today:** per `UNIVERSAL-GRAPH-CONTRACT.md`, Atlas's graph is explicitly a **derived, non-canonical projection** over normalized typed semantic records (`Node`, `Edge`, `Binding` as a distinct richer relation type, `Materialization` linking meaning to physical artifacts) — the graph is not the source of truth, the reconciled typed semantic world is.
- **IRIS:** SemanticGraph **is** the canonical program representation — "the surface syntax is a projection of the SemanticGraph, not the source of truth" (README, verified structurally by the existence of a real compiler pipeline that consumes `.iris` text and a decompiler path back to text).
- **Assessment:** superficially similar language ("the graph is canonical, syntax is a projection") but **inverted in what the graph represents.** Atlas's graph represents *facts extracted about arbitrary external source code with varying epistemic confidence*; IRIS's graph represents *the executable program itself, which it authored and fully controls*. IRIS has no analog of Atlas's `EpistemicStatus`/`EvidenceKind`/`Disposition` taxonomies because it has no "evidence about someone else's code" problem — its graph is definitionally ground truth for its own execution. Atlas's `Binding` concept (explicit typed interface/capability/protocol compatibility between graph nodes across repositories) has no clear IRIS analog since IRIS graphs are single-program, not federated across many repos.

### Compiler pipeline: Atlas compiler preservation clause vs IRIS's 10-pass pipeline

`UNIVERSAL-GRAPH-CONTRACT.md`'s "Compiler preservation" clause (compiler phases may optimize representation but may not erase externally observable graph identities/bindings) is a *policy constraint on a not-yet-fully-built Atlas compiler*. IRIS's 10-pass pipeline (monomorphize → defunctionalize → match-lower → fold-lower → effect-lower → neural-lower → layout → isel → regalloc → container-pack) is a concretely verified, working pass ordering for lowering a typed functional DAG to a native/CLCU execution target. **Assessment:** IRIS's pipeline is a reasonable reference architecture for "how do you lower a typed content-addressed DAG through progressively lower-level IRs while a compiler-preservation-style invariant holds," but Atlas has not yet built a comparable compiler over its own graph, so this is REFERENCE_ONLY — there is no current Atlas mechanism to concretely compare pass-by-pass.

### Semantic dimensions materialized: Atlas SYMBOL/TYPE/FUNCTION_IDENTITY/FUNCTION_SIGNATURE/CALL vs IRIS's node/type kinds

Atlas has only materialized SYMBOL, TYPE, FUNCTION_IDENTITY, FUNCTION_SIGNATURE, and (just-landed) CALL (dispatch always UNRESOLVED). CONTROL_FLOW/DATA_FLOW/STATE/EFFECT/OWNERSHIP/CONCURRENCY/PERSISTENCE are contractually named but **UNSUPPORTED** in Atlas today. IRIS, by contrast, has a complete (if partially-unverifiable) *program representation* covering control flow (via its DAG structure and `Guard`/`Match`/`Fold` node kinds), data flow (functional dataflow is definitionally exact in a pure DAG — no aliasing ambiguity because IRIS is purely functional), effects (an explicit 44-tag effect system with capability-guarded dispatch, verified in README and corroborated by `exec/effects_dispatch.iris`/`exec/capabilities.iris` file presence), and even a primitive cost/ownership-adjacent notion via its `CostBound` type and refinement types. **This is not a fair apples-to-apples comparison**: IRIS's dataflow/control-flow/effect facts are *definitionally exact* because IRIS controls the entire language and graph; Atlas's equivalent dimensions (once real) must be *extracted with uncertainty* from arbitrary third-party source in arbitrary languages, which is a fundamentally harder and differently-shaped problem. IRIS is a useful reference for the *target shape* of a CONTROL_FLOW/DATA_FLOW/EFFECT record once Atlas's extractors exist, but offers no shortcut for the extraction-with-uncertainty problem Atlas actually needs to solve for CONTROL_FLOW/DATA_FLOW/STATE/EFFECT/OWNERSHIP/CONCURRENCY/PERSISTENCE.

### Verification boundary: Atlas has none yet; IRIS's Lean kernel is a genuine reference

Atlas currently has no proof-kernel or formal-verification boundary in any of the read contracts. IRIS's Lean 4 kernel + IPC bridge is a real, partially-verified (not fully — see `sorry` findings above) reference for "how do you keep a natural-language-adjacent hot compiler/evolution loop honest via an externally-verified, structurally-separate kernel." REFERENCE_ONLY for Atlas at this stage — Atlas has no self-modifying/evolving execution loop that would need such a kernel yet.

## Discoveries

- **IRIS SemanticGraph node/edge/identity model: REFERENCE_ONLY.** Real and coherently documented at the level of node-kind taxonomy and content-address role, but the canonical implementation (`iris-repr` Rust crate) is absent from this repository, so full structural verification (exact edge representation, exact 20-node-kind enum) was not possible.
- **IRIS BLAKE3 content-addressing: REFERENCE_ONLY, with an important caveat.** What ships as `.iris` source is a non-standard, 64-bit-truncated derivative of BLAKE3, not the full 256-bit algorithm the wire format's own 32-byte `SemanticHash` field implies is canonical. Do not cite "IRIS proves BLAKE3 content-addressing at scale" without qualification — this repo only lets you verify a reduced mirror, not the real thing.
- **Absent Rust source for the "self-hosted" claim's most load-bearing crates: EXTERNAL_BOUNDARY.** Roughly 85 of the ~243 non-example `.iris` infrastructure files carry explicit "Mirrors the Rust ... in iris-repr / iris-compiler / iris-kernel / src/iris-kernel/src/kernel.rs" headers, spanning `repr/`, `codec/`, `compiler/`, `deploy/`, most of `evolution/` (including `full_evolve_loop.iris` and `iris_runtime.iris`, the top-level driver and runtime harness), all of `exec/`, `foundry/`, `interpreter/`, `lsp/`, `store/`, and `syntax/`. None of the Rust crates these comments name are present in this repository at this pin, and `.github/workflows/ci.yml` references a `cargo build --all-targets` step and ~13 `cargo test` targets for which **no `Cargo.toml` exists anywhere in the clone** — the published CI workflow cannot pass as configured against this tree. The practical implication: this GitHub repository, as cloned, is not a complete, self-building system. It ships a frozen compiled bootstrap binary, a self-hosted `.iris`-language mirror of most subsystems (useful as a design reference, not independently executable without the missing binary/toolchain), a genuinely complete and inspectable Lean 4 formal kernel, and a genuinely complete small C hardware backend (`iris-clcu`). Attribute mechanisms accordingly: do not credit "boj/iris" wholesale for mechanisms whose authoritative implementation is an unpublished, unverifiable Rust codebase.
- **IRIS Lean 4 proof kernel: REFERENCE_ONLY, genuinely verified as real (with a factual correction to the README's framing).** 2,941 lines, 0 `sorry` in the 20 inference rules and supporting eval/type machinery, 7 `sorry` in metatheory/correspondence proofs (`KernelCorrectness.lean` ×5, `Properties.lean` ×2) explicitly flagged by the authors as pending a Lean-version tactic port. Zero external Lean package dependencies. The IPC wire protocol is corroborated from both the `.iris` client and Lean server sides.
- **IRIS self-modification admission gate: REFERENCE_ONLY, with a concrete stub-code finding.** The visible `.iris` performance-gate logic (`meta/performance_gate.iris`, `meta/auto_improve.iris`) hardcodes the "slowdown" comparison term to a constant 100 (parity) rather than passing the candidate's actual measured timing — as coded, only the correctness (100%-trace-match) term can block a deployment. This may be an incomplete `.iris` mirror of a working native gate (which we cannot inspect), or it may reflect the real current state of the feature; either is possible and neither can be resolved without the absent native source.
- **IRIS evolution engine (NSGA-II/lexicase/novelty/MAP-Elites): REFERENCE_ONLY.** Real, substantial `.iris` implementations of standard multi-objective/quality-diversity evolutionary algorithms exist and are readable, but — as with the compiler and repr subsystems — several of the most load-bearing files in this exact subsystem (`full_evolve_loop.iris`, `iris_runtime.iris`, `result.iris`, `config.iris`) are themselves declared mirrors of an absent Rust original, so treat the `.iris` evolution code as a documented reference architecture, not as verified production behavior.
- **License: EXTERNAL_BOUNDARY for any verbatim-code absorption.** AGPL-3.0-or-later is confirmed from the LICENSE file text. This is a materially different obligation profile than prior MIT/Apache/CC0 donors; any future absorption decision involving copied IRIS code (as opposed to studying its architecture) must account for AGPL's copyleft/network-use terms. Architectural/conceptual study (which this census performs) does not itself trigger license obligations, but literal code reuse would.
- **iris-clcu C hardware backend: REFERENCE_ONLY.** Genuinely present, small (4 files), self-contained C99 implementing an AVX-512-optional container interpreter with scalar fallback, a CRC32-accelerated TLB-style map, and a TSO (total-store-order) synchronization ring — real, inspectable, no external dependencies. Not obviously relevant to Atlas's current roadmap (Atlas has no comparable low-level hardware execution substrate need yet), hence REFERENCE_ONLY rather than a stronger disposition.
